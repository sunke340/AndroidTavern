## 二、约束（决定了“怎么拆”而不是“拆不拆”）

1. **本机编不了 `:app`**：一次几百行的机械改名，错误只能在 CI 发现（4 分钟）＋真机验一轮。
   → 每批必须**小到能在一屏 diff 里看完**，且每批一个包。
2. **纯逻辑要落 `core/*` 才能被断言**：CI 的「纯 JVM 单测」job 跑 `./gradlew test`，
   `core` 的 168 条在那里跑；`app` 目前没有 `src/test`（有也能跑，但本机跑不了）。
   → 抽出来的规则优先落 `core`（本机 `tools/test-core.sh` 秒级验证），Android 相关的才留 `app`/`data`。
3. **先例已经证明这条路走得通**：`RevealPacer`、`RevealCatchUp`、`PromptOrderCompat`
   都是从它里面抽出来、带单测、行为不变的。
4. **每批都要能单独回退**：一个批 = 一个提交 = 一个 tag（`apk-mNNN`），坏了一键回到前一个。

## 三、批次（按风险从低到高，别跳）

### B0 · 先设底线，别一边拆一边涨

- 新增 `tools/check-viewmodel-size.sh`：把 `ChatViewModel.kt` 的**行数与 public 方法数**打出来，
  超过 `tools/viewmodel-budget.txt` 里的封顶值就红。
- 初始封顶 = 现在（3,792 行 / 121 个 public），**每批成功后下调一次**（棘轮）。
- CI 的「铁律检查」job 里跑它。
- 顺带把 [architecture-audit.md](dev/architecture-audit.md) 顶部加一句“数字是 11-26 快照，看 plan-chatviewmodel-split.md”。

**判据**：故意加 1 行 → CI 红；撤掉 → 绿。
**风险**：极低（一个新脚本 + 一个数字文件）。

### B1 · 抽「三级继承的生效值」（302 行规则 → 纯函数）

现在 18 个 `effective*` getter 把“会话 > 卡 > 预设 > 全局”的决策写死在 ViewModel 里。
这是**“界面显示 A、请求发 B”那类历史 bug 的源头**（[app/AGENTS.md](../app/AGENTS.md) 专门立了规矩：
生效值只能从这几个 getter 读）。

- 把决策抽成 `core/model/ConfigResolution.kt`：输入 `ConfigOverride?`（会话/卡/全局）+ 预设默认，
  输出一个不可变的 `EffectiveConfig`；纯函数、零 Android 依赖。
- ViewModel 里 18 个 getter 退化成 `effective.xxx` 一行转发（**名字不变**，UI 零改动）。
- 单测：每层覆盖 + “空集 ≠ null” + 采样五项顺序（会话 > 卡 > 预设 > 全局）。

**判据**：168 条原有单测 + 新增 ≥8 条全绿；UI 一行没改；真机抽 2 个会话验配置显示与实际请求一致。
**风险**：中低（规则本身有测试兜住，UI 不改）。
**预估**：ViewModel −250 行左右。

### B2 · 抽「发送前准备」，顺手把主线程重活挪走（P0-2）

`beginCompletion` 里 `scanWorldInfo()` + `PromptBuilder().build()` + 全量 token 预算
在 `viewModelScope.launch` **之前**跑，即主线程（长聊必掉帧，最坏 ANR）。

- 抽成 `core/prompt` 的纯函数 `prepare(request)`：世界书激活 → 正则 → 组装 → 预算裁剪，
  输入输出都是数据类；
- ViewModel 里改成 `viewModelScope.launch { val prepared = withContext(Default) { prepare(...) } ... }`；
- 单测：现有 fixture（`P1-7` 作者注、`P0-6` continue、世界书那批）**必须全部照旧通过**——
  这是“行为不变”的硬证据。

**判据**：所有 prompt/世界书 fixture 原样通过；真机：长会话发送不再卡首帧（日志 `发送 … Nms` 对照）。
**风险**：中（动了发送链路的主干，必须真机验一次）。
**预估**：ViewModel −150 行。

### B3 · SAF 导入四件套去重（4 份 × ~25 行）

`displayNameOf` + `openInputStream` + `readText` + `runCatching` + `notify` 在聊天/世界书/预设/正则
各写了一份（审查附录 C 记了行号）。

- 合成 `app/SafImport.kt` 一个 `readTextOrNotify(uri): String?`；
- 四个调用点各减 ~20 行。**零行为变化**。

**判据**：四处导入各导一次（真机）；CI 绿。
**风险**：低。
**预估**：ViewModel −80 行。

### B4 · `persistConnection()` 串行化（P2-3）

现在每个按键 `launch` 一个协程写 SharedPreferences，顺序不保证；`onCleared` 还会丢最后 600ms。

- 用一个 `Mutex` 或单消费者 channel 串行化写入；
- `onCleared` 里同步落一次（或用 `runBlocking` 的极短写）。

**判据**：连续快速改 baseUrl/model 后重启，值是最新的（真机 + 日志）。
**风险**：低中（并发，但面很小）。
**预估**：ViewModel ±0 行。

### B5 · `UiState` 分组建模（373 处引用，分四刀）

这一步**收益最大也最机械**，所以放后面、且分成四刀，每刀一个包：

| 刀 | 拆出什么 | 大约引用数 |
|---|---|---|
| B5-1 | `NavState`（`screen` / 详情 / 各 `open*Page` 的目标） | ~60 |
| B5-2 | `ConfigState`（连接参数 + 采样 + 三级选择） | ~120 |
| B5-3 | `GenState`（transcript / 生成中 / 揭示游标 / swipe） | ~140 |
| B5-4 | `EditState`（卡编辑草稿 / 人设草稿 / 预设编辑 / 正则） | ~50 |

规则：**字段名与类型都先不动**，只改归属（`state.screen` → `state.nav.screen`），
一次性替换 + `grep` 复核，不做行为改动。四刀做完，`UiState` 只剩组合与默认值。

**判据**：每刀 CI 绿 + 一个包；真机回归清单（进聊天/发消息/切卡/配置页/设置页）。
**风险**：机械但面广（一次 60~140 处）。**回退点必须打 tag。**
**预估**：`UiState` 从 259 行的单体变成 4 个 60~80 行的组 + 一个 40 行的组合类。

### B6 · 消息分页（P1-5，最后做）

`transcript` 全量载入 + UI 下标 ↔ DB 行号强耦合，与 `data/AGENTS.md` 的「分页读」直接冲突。
这一批要动 DB 读法与滚动锚点，**必须单独一轮**，不跟前面混。

**判据**：300+ 条会话首屏 < 200ms；滚动到顶再往上翻页；删/撤销后下标不串行。
**风险**：高（数据正确性）。
**预估**：ViewModel 结构变化最大，但换掉的是“最危险的那部分”。

## 五、节奏与验收

- 一批 = 一个提交 = 一个 `apk-mNNN` tag；**真机只验“行为不变”**（回归清单：
  进聊天 / 发一条 / 切档 15→70 / 切卡 / 会话配置 / 预设编辑 / 导入卡 / 分享）。
- 每批结束更新本页“已完成”列与 `status.md`；B0 的预算值同步下调。
- 任何一批 CI 红两次以上 → 退回上一批，重新切小，不硬推。

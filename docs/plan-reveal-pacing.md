# 流式回复的"揭示节奏"方案（待评审）

> 状态：**方案阶段，代码未动**。写给第三方评审用，所以把"证据 / 决策 / 被否掉的选项 / 风险"都摆出来。
> 关联：[M27](dev/verification/2026-11-26-M27.md)、[M28](dev/verification/2026-11-26-M28.md)（v177/v179/v180 三版失败的经过）、
> [app/AGENTS.md](../app/AGENTS.md)「聊天串流跟随」段、[pitfalls](dev/pitfalls.md)。
> 本文口径：只讲**显示**，不碰请求、落库、导出、提示词。

## 0. 一句话

把"**收到文本**"和"**显示文本**"拆开：收到的全文进缓冲，界面只渲染"已揭示的前缀"，前缀按用户选的速率（字/秒）匀速推进，气泡高度等于这段前缀自己排版出来的高度。
**代价**：落库/收尾后画面可能仍在打印（需要让"揭示游标"活过收尾）。

---

## 1. 现状与问题（有实测数据）

### 1.1 现象

用户三条反馈（2026-11-26 晚）：

1. 点发送后整个列表先往下滑一下，气泡才出来 → **已修**（v177，根因：平滑高度基线把 0 当成"上一个高度"）。
2. 用户消息滚出视口再滚回来，动作行重新浮现 → **已修**（v179，根因：入场动画在行被 LazyColumn 回收后重播）。
3. **不满一屏时，AI 回复逐行抬升，整屏抽搐** → 两次试图修（v179 / v180）都失败。

### 1.2 实测（v180 的 `串流帧` 诊断日志，2026-11-26 23:32）

设备 vivo V2405A / Android 17(sdk 37)。一次 503 字的回复，19 秒。日志每 100ms 一条：

| 时刻 | 槽位高 | 自然高 | 平滑高（画面实际高度） | 桥（=自然−平滑） |
|---|---|---|---|---|
| 14.122 | 399 | 280 | 280 | 0 |
| 14.354 | 679 | **560** | 280 | **280** |
| 14.703 | 749 | 630 | 629 | 1 |
| 15.751 | 1589 | 1470 | 1470 | 2 |
| 16.334 | 2079 | **1960** | 1470 | **490** |
| 16.792 | 2499 | 2380 | 2000 | 380（随后收尾，**直接丢掉**） |

由此得到的关键数（px，密度下 1 行 ≈ 70px）：

- **平均到达率** ≈ 125 px/s（≈ 1.8 行/s）；文本速率 ≈ 26 字/s（503 字 / 19 秒）。
- **到达是攒包的**：出现"583ms 一个字没来，然后 490px（7 行）一次到"。
- 画面速度在 **0 与 ~1900 px/s 之间来回**（追上就停 232/270/583ms，来字就猛冲）→ 这就是用户说的"抽搐"，是**走走停停**，不是布局抖。
- 橡皮筋全程没参与（`raw/visual` 恒 0）；列表自身滚动偏移全程 0。
- `槽位高 − 自然高` 恒等于 119px（动作行预留），说明两层高度没有错位。

### 1.3 为什么两次修都没修好

| 版本 | 假设 | 结果 |
|---|---|---|
| v179 | 短列表没有滚动距离 → 橡皮筋拉/弹 | ❌ 用户驳回；日志显示抽搐时**没有一条 rubber 记录** |
| v180 | ① 入场期"自然高度 vs 槽位高度"错位 ② 追高用 tween 把速度清零 | ❌ 用户驳回；实测 ① 不是主因（槽−自然 恒定 119px），② 只把"走走停停"的时长缩短 |

**教训**：问题不在"哪条通道有 bug"，而在"**用滞后换平滑**"这个机制本身——在攒包输入下，滞后与平滑度只能二选一，峰值滞后 = 一次攒包的大小（实测 7 行）。

## 2. 目标

1. 回复**逐字匀速出现**（用户原话："让文字匀速打印"），不再整块冒。
2. 气泡长度的增长**跟着打印走**，不是靠动画去追布局。
3. 节奏由**用户选的档位**决定；程序不偷偷加速。
4. 不改变任何非显示行为：请求体、提示词、落库内容、导出、`查看请求` 全部是全文。

**非目标**：不做"打字机音效/光标闪烁"这类装饰；不改动对话历史里的既有消息（只影响"正在出现的这一条"）。

---

## 3. 方案

### 3.1 数据流

```
SSE delta → inflight.text（全文，现有逻辑不变，不新增缓冲）
                    │
                    ├── 揭示游标 revealed（页级状态，按 N 字/秒推进）
                    │
                    └── 渲染 inflight.text.take(revealed)
                              │
                              └── 气泡高度 = 这段前缀的自然排版高度（布局即真相，无夹扯、无桥接）
```

**关键点**：没有"缓冲队列"这个新概念——`inflight.text` 本身就是缓冲，游标只是它的下标。所以 ViewModel 侧不需要改流式路径，改动集中在 `ChatScreen` 的渲染与一个页级状态。

### 3.2 推进器

```
每帧（withFrameNanos）：
    pending += rate * dt          // rate 单位：字/秒；pending 是浮点累加
    take = floor(pending)         // 15 字/s 在 60fps 下是 0.25 字/帧，必须浮点累加，否则永远不动
    revealed = min(revealed + take, text.length)
```

- 有未显示的字才推进；没有就停（模型慢时画面跟着到字走，这是应该的）。
- **减动效**（系统"移除动画"）时按"不限速"处理（等价关掉打字机）。

### 3.3 档位（唯一旋钮）

| 档 | 速率 | 500 字回复的打印时长 |
|---|---|---|
| 慢 | 15 字/s | ~33s |
| 中（默认） | 35 字/s | ~14s |
| 快 | 70 字/s | ~7s |
| 极限 | 不限速（= 现有行为） | 模型多快就多快 |

考虑再加一档 **8 字/s** 给"想慢慢看"的场景（待定，见 §7）。

**没有"最长打印时间"上限**（之前提过 60 秒，已否掉：那是把节奏从用户手里抢回去的魔法常数，且无原则可依）。
嫌慢就改档位数值或加档，档位就是那个旋钮。

### 3.4 打断与逃生口

| 事件 | 行为 |
|---|---|
| 点一下正在打印的气泡 | 立刻补满 |
| 点「停止」 | 立刻补满（用户按停止就是要看结果） |
| 退出聊天页 / 切会话 | 立刻补满（游标不跨页面） |
| 发下一条 / 重新生成 / 换 swipe | 上一条立刻补满；新一轮从头开始 |
| 进入"重新生成"的收缩窗口 | 立刻补满（收缩与打印不能同时驱动高度） |

### 3.5 停滞看门狗（防 bug，不是防用户的节奏选择）

> 还有未显示的字符，但 `revealed` 连续 **5 秒**没有推进 → 直接补满，并记一条 `chat 打印停滞，补齐（剩余 N 字）`。

理由：游标若因 bug 停住，用户看到的是"消息被永久截断"，像丢字。正常使用永远不触发。

### 3.6 游标活过收尾（这是本方案唯一的架构性改动）

现在的收尾：`inflight` 消失 → 该行换成库里的整条消息（`m{dbId}`）→ 如果游标只在 `inflight` 期间有效，**落库那一帧会瞬间补满**，慢档等于白选。

改法：游标放在**页级**，并且记"当前在打的是哪一行"：

```
printing = (messageKey: String?, revealed: Int, lastProgressAt: Long)
```

- 开轮时：`messageKey = inflight.uiKey`（`p{seq}` 或重新生成时的 `m{dbId}`），`revealed = 0`；
- 收尾时（`inflight` 变 null 的那一帧）：把 `messageKey` 改成"刚落库的那一行"的 `uiKey`（`m{dbId}`，即 `state.rows.lastOrNull()`），`revealed` 不动；
- 该行的渲染：`if (printing.messageKey == row.uiKey) row.content.take(printing.revealed) else row.content`；
- 打满 / 任一打断事件 → 清空 `printing`。

这样"落库 → 继续打印"不需要改 ViewModel、不需要改行模型（`ChatRow`），只是多一个页级状态 + 一处渲染判断。

### 3.7 与现有串流机制的交接

| 现有机制 | 在新方案里 |
|---|---|
| 画布桥接（`translationY = 自然 − 平滑`、`followBridgePx`） | **打印期间恒 0**（布局即真相）。它只在"不打印"的路径上保留（例如后续别的场景） |
| `smoothHeight` / `streamHeight` 追高 | 打印期间不再需要；保留给"重新生成收缩"那套（r2 §13.1 C1） |
| 入场动画（`revealFromBottom` 槽位增长） | 保留（新行仍然从下往上长）。与游标同时作用于高度，需真机确认两者叠在一起是否顺 |
| 落库前的动作行/版本条预留（`chromeHeight`） | 保留不变（收尾那一帧高度不跳的前提） |
| 占位气泡（`重新生成中` + 呼吸点） | 保留，判据改成"还没收到第一个字"，而不是"还没打印第一个字"（否则占位会一闪） |

## 4. 被否掉的选项（附理由）

| 选项 | 否掉的理由 |
|---|---|
| **追平时间 T**（`rate = backlog/T`，弹簧或一阶低通） | 实测就是"走走停停 + 最新 7 行藏在输入框后面 150–600ms"。滞后与平滑度不可兼得 |
| **高度匀速 px/s**（夹"报给布局的高度"） | 需要夹高+手裁，且 px/s 随屏幕密度变；更要紧的是它把"字"的节奏让给了"高度"，用户要的是"一个字一个字" |
| **不跟（浏览器式）** | 攒包一来内容整块上跳 4–7 行（实测），2026-11-24 已被用户否过 |
| **自动换档**（按 token 速度/剩余字数切档） | 打印速度会中途变，观感是"突然加速"，且把用户选的慢档悄悄改掉 |
| **最长打印时间上限（60s）** | 魔法常数、替用户改节奏；且无法从"模型耗时/人眼阅读速度"推出通用值 |
| **字符级 API 先收再吐（独立缓冲队列）** | 与"游标 = 下标"等价，但多一份状态、多一处可漏水的地方 |

## 5. 风险与未验证点

1. **每字一次重排的开销**：现在每 delta 重排一次（~26 次/s）；快档 70 字/s 会到 ~70 次/s。长回复（2000+ 字）时是主要开销。缓解：每帧吐 2–3 字（视觉等价），或只在可见行变化时重排。
2. **收尾那一帧的游标转移**：`inflight` 消失与 `rows` 新增同一帧发生，转移必须原子（在同一个 `LaunchedEffect(state.inflight)` 里读 `rows.lastOrNull()`），否则会补满或错行。
3. **入场动画 × 游标**：两个高度驱动源同时存在（入场 380ms + 每帧几个像素的游标），需真机看是否顺、是否有一帧错位。
4. **重新生成（收缩窗口）**：收缩期间必须不打印；收缩结束、正文开始长时的衔接需真机确认。
5. **版本条/动作行**：收尾后它们按现有预留逻辑出现，而正文还在打印 → 高度不能跳（现有 `chromeHeight` 预留仍然成立）。
6. **复制/选中**：打印期间选中只能到前缀（决定：动作行的「复制」作用于**全文**）。
7. **长回复 + 慢档**：2000 字 = 133 秒。这是"慢"的字面含义，逃生口是点气泡。**评审请判断这个取舍是否可接受。**
8. **工程约束**：本机编不了 `:app`（2 核 / 1.7 GiB，无 Android SDK）、无模拟器 → 每轮只能靠 CI 出包 + 用户真机回执（含 15–20 分钟下载），预计 1–2 轮。这也是本方案"尽量少动架构"的原因。

## 6. 验收标准（真机 + 日志）

| # | 怎么造 | 过 = 看到什么 |
|---|---|---|
| 1 | 不满一屏的会话里发一条长回复，慢/中各试一次 | 文字**逐字匀速**出现；气泡跟着长；没有整块冒 |
| 2 | 同上，盯整个画面 | 只有"行满跳一行"（≤1 行/次）；没有 4–7 行的整块位移 |
| 3 | 同上，看 `tag=scroll 串流帧` | `桥` 恒 0；`自然` 单调增；增长与字数成正比 |
| 4 | 打印途中点气泡 | 立刻补满，后续不再动 |
| 5 | 打印途中点停止 | 立刻补满，状态栏「已停止」 |
| 6 | 打印途中退出聊天页再进 | 直接是全文 |
| 7 | 生成完（落库）但还没打完 | **继续打印**，不瞬间补满；版本条/动作行不跳 |
| 8 | 打印途中发下一条 / 重新生成 | 上一条立刻补满；收缩窗口不打印 |
| 9 | 极限档 | 与现有行为一致（模型多快就多快） |
| 10 | 系统开"移除动画" | 等同极限档 |

## 7. 待评审确认

1. **档位**：`15 / 35 / 70 / 不限` 够不够？要不要加 **8 字/s** 这种更慢的档？
2. **不需要"最长打印时间"上限**这个判断是否成立？（代价：2000 字慢档 133 秒，逃生口只有"点气泡"）
3. **游标活过收尾**（§3.6）是不是最小可行改法？有没有更稳的落点？
4. **每字重排的性能**是否需要提前做"每帧多字"的控制？在什么阈值（字数 / 设备档位）？
5. 交互上，"点气泡 = 补满"是否与将来的手势（长按选字、滑动）冲突？

# ADR 0001：兼容 = 格式兼容 + 行为复刻

- 日期：2026-11-21
- 状态：采纳
- 相关：[plan.md](../plan.md)

## 背景

「兼容原版酒馆」有三种实现，代价差一个数量级：原生重写、WebView 套壳、原生 UI + 复用原版 JS 逻辑。不先钉死一个，后面每个功能都会重新吵一遍"这算不算兼容"。

## 决策

**原生重写，兼容性落在两处，且都可自动验收：**

1. **文件格式兼容（双向）**：PNG 卡（`tEXt` 的 `chara` / `ccv3`）、charx、JSONL 聊天、世界书 JSON、预设 JSON。要求 PC 版 ST ↔ 本 App 往返可用。
2. **提示词行为兼容**：同一套输入，本 App 发出的 `messages[]` 与 ST 1.19.1 **逐条相等**，以 golden fixture 断言。

UI、设置项命名、配色、交互一概不要求兼容。

## 理由

- 用户真正在意的迁移成本是「我攒的卡和聊天记录能不能带走」，不是「按钮在不在同一个位置」。
- 行为兼容如果不设成可测断言，就只能是"看起来差不多"，而 LLM 对提示词差异极其敏感——差一个换行、一个 role，表现就不同。
- 反向方案（复刻 JS）要么拖一个 JS 引擎（QuickJS）做桥接，要么整包 WebView，都违背"原生"这个前提。

## 代价

- 需要先搭测试台（本机跑原版 ST + 假 API 录制请求体），在写业务代码之前。
- 每个 P0/P1 特性都要配一个 fixture，前期节奏会显得慢。
- 原版内部行为（如 `names_behavior`、`squash_system_messages`、递归扫描）只能靠读源码 + 对拍逼近，不能保证 100% 覆盖；未覆盖项要在兼容矩阵里明确标注"近似"。

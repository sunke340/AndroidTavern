# ADR 0002：单进程，不做前后端分离

- 日期：2026-11-21
- 状态：采纳
- 相关：[plan.md](../plan.md)

## 背景

原版 SillyTavern 是 Express 服务端 + 浏览器前端。「复刻一个原生安卓版」时很容易顺手把这套形状也搬过来（App 里跑一个本地 HTTP 服务，UI 连 `127.0.0.1`），或者干脆 WebView 套壳。这里记下为什么不这么做。

先看原版**为什么**要分。它的每一条理由都成立，但基本都是浏览器约束：

| 原版分前后端的理由 | 在安卓单进程里是否成立 |
|---|---|
| 浏览器不能读写任意文件（卡、聊天、世界书都在磁盘上） | ❌ 不成立。App 用 SAF / 私有目录，还能直接做 PNG chunk 改写 |
| 浏览器有 CORS，直连各家 API 会被拦 | ❌ 不成立。OkHttp 没有 CORS 概念 |
| 浏览器不能长时间跑任务（向量化、图片生成） | ❌ 不成立。WorkManager / 前台服务 |
| 多用户、多标签页共享一份数据 | ❌ 不成立。一台手机一个用户，无标签页 |
| API Key 不能落到浏览器里，所以放 `secrets.json` | ❌ 反而更弱。Keystore + EncryptedSharedPreferences 比明文 JSON 强 |
| 插件/扩展从磁盘加载，服务端才能读 | ❌ 不成立。APK 内的代码就是"插件" |
| 一个数据目录被多台设备访问（手机、平板、PC） | ⚠️ 唯一真实成立的一条。但这是"同步"问题，不是"前后端"问题 |

## 决策

**单 APK、单进程、无本地 HTTP 服务、无 WebView。**

分层照旧，但边界不是 HTTP，而是纯 Kotlin 的模块边界：

```
UI (Compose)
   ↓
domain / usecase
   ↓
repository 接口 ──┬── Room（消息、卡、世界书）
                  ├── SAF / FileStore（导入导出、PNG/charx/JSONL）
                  └── AiClient（OkHttp + SSE）
```

被"后端"承担过的职责，就地分配：

| 原版后端职责 | 本 App 对应物 |
|---|---|
| 文件 IO、PNG chunk 解析 | `:core:card-format` / `:core:chat-format` |
| 代理 LLM 请求、绕 CORS | OkHttp 直连（`AiClient`） |
| 存密钥 | Android Keystore |
| 长任务、分批 | WorkManager / 前台服务 + 协程 |
| tokenizer 服务 | `:core:tokenizer`（jtokkit，进程内） |
| 向量检索 | 进程内 ONNX（可选，后期） |

## 为什么认真考虑过还是否掉了

**1. 本地服务不省代码，只加复杂度。** localhost 只是把函数调用换成 HTTP + JSON 序列化，同时引入：服务生命周期（Doze 杀进程后 UI 变砖）、端口占用与自启、两个进程的版本一致性、SSE 穿透 loopback 的取消语义（协程里 `cancel()` 一行的事，跨进程要自造协议）。收益是零。

**2. 安卓上"常驻后台服务"本身是逆着平台设计的。** 前台服务要挂通知、要声明类型，Android 15 还在收紧。为了一次单轮对话维持一个 Node 进程，是拿最贵的资源换最不值的东西。

**3. 堆栈翻倍。** 原版那份 JS 逻辑（prompt 组装、世界书激活）本来就要用 Kotlin 重写一遍才叫"原生"。既然已经重写了，服务端就没有任何存在意义——它只是同一份逻辑的第二个副本。**两份实现 = 两份 bug，且没有任何机制保证它们一致。**

**4. WebView 套壳已单独否决**（plan §1 方案 B）：它不解决"原生"，还把 Node 搬到手机上——nodejs-mobile 要拖几十 MB 原生库，插件体系依赖 `fs` 与 npm 生态，手机上既跑不动也调不动。

## 代价与预留缝

不做前后端会丢掉两样东西，都在设计上留了出口，成本为零：

1. **跨端复用**：所有 `:core:*` 强制纯 JVM（不 import `android.*`）。将来要桌面版 / 命令行 / KMP，同一份 prompt 与世界书逻辑直接编进去，不需要另起服务。
2. **跨设备同步**：数据以「ST 兼容的 data 目录布局」为可导出形态。用户想同步，用 Syncthing / 网盘同步那个目录即可，**不需要我们写后端**。真要中心化同步（多设备合并冲突），那是独立产品决策，等有需求再说。

## 未来可能推翻本 ADR 的场景

- **"手机当 PC 版 ST 的客户端"**：如果真实诉求是"躺在床上用家里 PC 上那套 ST"，那不是复刻，是瘦客户端，得对接 ST 那套绑浏览器 session 的 REST 接口（`/api/backends/*`），脆弱且受制于人。作为独立模式评估，不混进主线。
- **设备上跑 7B 级本地模型**：推理放进 JNI 还是独立进程，届时按内存与崩溃隔离再定。这是进程边界问题，不是前后端问题。

## 一句话

Node 只在**开发期**出现：跑原版 ST 录 golden fixture 当基准。产品里没有 Node，没有 server，也没有 localhost。
